# Authorisation matrix

Access in BlakPath is always permission-checked. A user's existence grants
nothing. Access flows from an active membership of one organisation, to the
roles on that membership, to the permission keys those roles grant. The
catalogue in `src/lib/permissions/catalog.ts` is the source of truth for keys.
This document is checked against that catalogue and against every handler in
`src/app/api` by `tests/unit/authorization-matrix.test.ts`.

> BlakPath never determines Aboriginality. No permission grants a power to
> auto-decide, score, rank or infer identity. The most a role can do is let an
> authorised human record a decision that human has made.

## System role grants

Built-in templates, in `src/lib/permissions/roles.ts`. A checkmark means the
template grants that key. Applicant (`applicant`), Applicant Representative (`applicant-representative`), Intake Officer (`intake-officer`), Case Officer (`case-officer`), Genealogy Officer (`genealogy-officer`), Elder / Cultural Authority (`elder-cultural-authority`), Committee Member (`committee-member`), Committee Chair (`committee-chair`), Records Officer (`records-officer`), Organisation Administrator (`organisation-admin`), Platform Operator (`platform-operator`).

Separation of duties is in the templates themselves:

- `organisation-admin` administers people and configuration and holds no
  `evidence:*`, `decision:*`, or `certificate:*` key.
- `case-officer` cannot `decision:finalise` or `certificate:sign`.
- `committee-member` can vote and cannot finalise or sign.
- `committee-chair` may finalise and sign. No system role holds
  `calendar:delete-any`.
- `platform-operator` holds only `break-glass:request`. Requesting and
  activating break-glass checks the `users.isPlatformOperator` flag, not that
  key.

The catalogue key for the audit trail is `audit:view`. It is granted to
`organisation-admin` and included in the break-glass read bundle. It gates the
tenant audit viewer, CSV export and monthly review routes under `/api/audit`.
Those read and append only the caller's own tenant chain, never platform-chain
events or another tenant's.

## Routes

Every exported handler is a row. "Deny actor" is who the integration test
authenticates as for the non-success probe. Session routes use a real
membership and the role's database grants. `allowProbe` in
`src/lib/permissions/route-matrix.ts` is set only where an empty tenant can
return 2xx. An id route often returns 403 both when the caller lacks the key
and when the row is missing, so those rows are deny-only. `GET /api/health`
and `GET /api/ready` are public dependency checks and are not called, because
they reach Redis and object storage. `GET /api/live` is the liveness probe.
`POST /api/csp-report` is a public browser report sink, so its probe only
checks that a non-report media type is refused. `GET /api/mcp` always returns 404. `POST /api/public/verify/[code]` takes no session: the printed code is the
capability, and the response never includes the recorded holder details.
`GET /api/public/correspondence/[token]/certificate` also takes no session: the
letter link is the capability. Sending a letter (`.../send` and
`.../notify`) needs a fresh sign-in because it releases case information to
the applicant. Reading a meeting pack (`GET /api/meetings/[id]/pack`) also needs
a fresh sign-in, and both a view and a refusal are audited.
`POST /api/organisations/applications` answers 403 for an unknown organisation
or one that has not opened public applications, before the session is read.
For an open organisation it needs an active membership there plus
`application:create`. It is a session-cookie mutation, so it is not under the
guard-exempt `/api/public` prefix.

## Keys with no HTTP route

These catalogue keys are granted by a template and enforced inside a domain
service, but no handler under `src/app/api` calls `requirePermission` or
`requireAny` for them. A new key has to land in a route gate or in this list
or the drift test fails.

- `evidence:read-assigned` — Included in the break-glass read bundle. Download checks evidence:download.
- `break-glass:request` — The platform-operator template grants it. Request and activate check users.isPlatformOperator, not this key.
- `group:manage` — addGroupMember has no route. Group list uses team:manage or membership:manage; create uses group:create.
- `client:assign-team` — assignClient has no route.
- `mcp:read` — API-key scope. POST /api/mcp authenticates the key, then hasMcpScope checks the key permissions. No session route checks it.
- `mcp:read-pii` — API-key scope. MCP tools omit direct identifiers unless the key holds it. No session route checks it.
